# build_mlp_lut.py 分析与可借鉴点

> 同事提供：完整模拟 FFN 模块的“表蒸馏”，小数据有效、大数据失效。

## 1. 这个脚本在做什么

1. **TargetFFN**：一个随机初始化的 FFN（2048 → 4096 → 2048），作为被蒸馏的目标。
2. **MappingMLP**：把输入 2048-dim 映射到 1-dim score（随机初始化，eval 模式，不训练）。
3. **排序 + 强制均匀坐标**：按 score 排序，给 1000 条数据强制赋予 0~1 的均匀坐标。
4. **InterpolationModel**：输入左右邻居坐标 + 中心坐标 + 左右邻居的 GT 输出（2048+2048），预测中心 GT 输出（2048）。
5. **训练**：Full-batch 训练 500 epoch，与线性插值 baseline 对比。

## 2. 为什么小数据有效

- **数据量小（1000 条）**：1D 排序后相邻样本在原始空间中可能恰好也有些邻近关系（因为随机投影保留了部分结构）。
- **函数平滑**：TargetFFN 是随机网络，输出在输入空间局部相对平滑，最近邻插值/MLP 插值都能拟合。
- **MLP 记忆能力强**：4099 → 2048 → 2048 的 MLP 对 1000 个局部模式足够记忆。
- **坐标均匀分布是人为构造的**：保证了训练时邻居关系固定且可学习。

## 3. 为什么大数据会废

本质原因是：**把高维输入硬压到 1D 坐标，并训练 MLP 做邻居插值，不可扩展。**

| 问题 | 解释 |
|---|---|
| **单 1D 投影信息损失** | 2048-dim 输入压到 1-dim score，大量结构被压扁。大数据下这种投影会把不相干的样本排在一起，邻居关系失去意义。 |
| **邻居关系不稳定** | 数据量增大后，按 score 排序的相邻样本在原始空间中往往并不相邻，导致插值目标自相矛盾。 |
| **MLP 插值器需要记忆所有局部模式** | InterpolationModel 输入包含左右 GT（2048+2048），输出 2048。每个“位置”都要记忆一个局部映射；大数据下参数量远不够。 |
| **均匀坐标分配不成立** | 大数据的真实分布不会在 1D score 上均匀分布，强行 linspace 会导致某些区域样本过密、某些区域过疏。 |
| **不是真正的 LUT** | 这里没有“表”，只有一个 MLP 插值器。查询时没有固定索引，而是依赖邻居 GT 和 MLP 计算。 |

## 4. 与项目红线的冲突

项目红线第一条：**动态参数必须通过 LUT 查表生成，不能是 MLP/HyperNetwork/其他前馈网络。**

这个脚本中的 `InterpolationModel` 正是一个前馈 MLP（4099 → 2048 → 2048），输入 query 和邻居 GT 后输出预测。这违反了红线。

即使 `MappingMLP` 是 eval 模式不训练，它仍然是一个前馈网络用于生成地址；`InterpolationModel` 更是直接生成输出。因此这个方案不能直接采用。

## 5. 有什么值得借鉴

虽然不能照搬，但有几个思想可以转化到我们的 LUT 框架内：

### 5.1 LUT 条目之间做插值，而不是最近邻

当前 v5 的 `LUTGroup` 是**最近邻查表**：索引 round 到整数 bin，直接取该 bin 的均值。

同事脚本的核心思想是：**相邻 LUT entry 之间应该可以插值**。这个思想本身是对的，而且可以不用 MLP：

- **1D address**：线性插值（根据 query 到左右 bin 边界的距离加权）。
- **2D address**：双线性插值（根据 query 到四个角 bin 的距离加权）。
- **Tree address**：树结构天然是分段的，插值不太直接，但可以在叶子层附近做平滑。

这种固定插值权重是 query 位置的确定性函数，不引入可学习前馈网络，**不违反红线**。

### 5.2 多个地址表 + 输出相加

同事用左右两个邻居的 GT 来预测中心。我们的 `LUTGroup` 已经有 `num_tables` 个表输出相加的集成结构，比他更通用。

### 5.3 地址应该保留输入空间的局部结构

同事用随机 MLP 映射到 1D，然后排序。我们的 tree address 本质上也是做这件事，但：
- tree 的 split 是**数据驱动**的（最小化残差方差），不是随机投影。
- tree 的叶子节点存储均值，不需要邻居 GT 作为输入。

所以 tree address 已经覆盖了同事想做的“把高维输入映射到离散地址”这一步，而且比他更鲁棒。

## 6. 可以直接吸收到 v5 的改进

### 6.1 给 2D address 加双线性插值

当前 `Address2D.compute_indices` 返回整数 bin 索引。可以改成返回浮点坐标，在 `LUTGroup` 里做双线性插值：

```
out = w00 * table[b0, b0] + w01 * table[b0, b1] + w10 * table[b1, b0] + w11 * table[b1, b1]
```

其中 `w00/w01/w10/w11` 由 query 在 bin 内的相对位置决定。

优点：
- 不增加参数量
- 输出关于输入连续平滑
- 仍属于 LUT 查表，符合红线

### 6.2 给 tree address 加叶子平滑

Tree 的叶子是硬划分，相邻 query 如果落在不同叶子，输出会跳变。可以加：
- 相邻叶子 entry 的均值平滑（让相邻叶子值接近）。
- 或在 tree 深度较浅时，用叶子边界的线性过渡。

但这需要更谨慎设计，以保持 O(1) 查表。

## 7. 结论

- **同事脚本不是 LUT，是 MLP 插值器**，大数据失效是因为高维→1D 投影损失 + MLP 记忆瓶颈。
- **不能直接采用**，因为违反项目红线。
- **可借鉴的核心思想**：LUT entry 之间做固定权重插值，而不是最近邻硬查表。这个改进可以加到 v5 的 `LUTGroup` 里，且符合红线。
- **建议优先级**：在 o_proj 实验跑通后，给 2D/tree LUT 加插值，看能否进一步提升质量。
