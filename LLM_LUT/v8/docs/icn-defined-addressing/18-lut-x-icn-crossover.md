# 18 — v6 LUT × ICN 矩阵交叉分析（v6+v8 与 14 号矩阵怎么配合）

> 矩阵总纲见 14 号，总结论全文见 16 号。本文不修改矩阵（9 行已于
> 2026-09-28 全判完结），只做交叉分析：v6 LUT（计算替代）+ v8
> （LUT serving 管线）与"named inference state"这条线的关系。
> 判文纪律沿用矩阵政策：过程计数器优先，负结果必须说清"否在哪个
> 环节、regime 边界在哪"。

## 0. 一句话结论

**能配合，但不能把 LUT 塞进矩阵当新一行。** 矩阵管的是 serving
侧 inference state（KV/checkpoint）的命名/寻址/驻留；LUT 是
**静态模型资产 + 前向内计算替代**，不在同一层。正确的配合方式是
三个交点：一个真 regime 问题（交点 A，值得做实验）、一个叙事同构
（交点 B）、一个经济学翻转的候选方向（交点 C）。

## 1. 为什么 LUT 不是矩阵的第 10 行

矩阵的立项纪律（14 号 §研究问题）：每个机制必须各自解决一个
真实存在的问题，不成立的机制也要给出 regime 边界。

LUT 不满足"搬进矩阵"的两个前提：

1. **它不是状态管理问题。** 表是只读、随模型版本固定的资产，
   不存在命名解析、驻留层级、并发合并这些运行期问题——这些在
   权重加载时就已经结束了。
2. **它没有外部性链条可研究。** 矩阵每一行的价值都来自某种
   稀缺资源的竞争（HBM、带宽、计算时间）。LUT 的存储和查询
   开销是结构性的、已知的（见 §3 交点 A），不构成新的机制
   问题。

硬塞进去会得到一行"✅ 天然成立，无事可做"——按矩阵纪律这是
噪音不是行。

明确排除两类伪证据：

- **"LUT 跨 worker 复制"不是行 5 的实验证据。** 行 5 研究的是

## 3. 交点 A：LUT 常驻 HBM 与 KV 的容量竞争（唯一值得实验的交点）

### 3.1 问题

三层 LUT（L37/38/39）在 serve 时的 HBM 足迹：

- coarse table：16384×2048 fp16 ≈ 64 MB/层
- residual table：32×65536×64 fp16 ≈ 256 MB/层
- 合计 ≈ 320 MB/层，三层 ≈ **1 GB 常驻**

矩阵行 4 的核心判文：**"落点决定一切"——驱逐到便宜层则状态可
召回，驱逐到虚空则重算回潮 2.9–4.4×**（16 号 §5.1 P3，tier 满
→ LRU 踢 → 块真消失，trace 单块一生被踢数百次）。

LUT 的 1 GB 常驻把 KV 的有效容量往紧一档推。在 sp96 式紧容量
regime 下，LUT 省的 FFN 计算可能被 KV 回潮吃掉。这是 LUT 与
矩阵相遇时**唯一有外部性链条**的地方。

### 3.2 实验设计（E2 testbed，改动小）

一格 = 独立集群（4 worker × 2 A800-80GB），worker 侧加载
v8 LUT 插件（L37-39 bundle，gate 修复版），其余走 11 号 runbook：

| 维度 | 取值 |
|---|---|
| workload | open-loop（poisson + zipf s=1.6，避开行 7 的风暴 regime，隔离变量） |
| spill | {无限 sp-1, 96MB sp96} |
| LUT | {off（dense serve）, on（三层全装）} |
| reps | ≥2 |
| 策略 | b3（放置控制是另一个变量，本实验先不叠） |

**可执行 runbook：`20-lut-e2-crossover-runbook.md`**（代码改动、
门禁、正式格命令、预登记判文阈值全在里面；worker 侧插件为
`icn_proto/lut_patch.py`，HF 路径不 re-apply gate，与 vLLM 插件
语义不同，勿混用）。

**判读指标（过程计数器优先，不看终局比分）：**

- sp96 × LUT on 相对 LUT off：hit 跌幅、new_tok 涨幅、evict/recall
  链 trace（LUT 占用是否把 kick 计数推高）。
- 对照 16 号 §5.1 P3 的 2.9–4.4× 回潮量级：若 LUT on 的回潮
  增量显著小于 FFN 节省（saved compute 需另计或按理论值估算），
  则交点 A 判"容量竞争可忽略"；若回潮增量吃掉甚至反超节省，
  判否，并给出边界（tier 容量多大以上 LUT 无害）。

### 3.3 预判与负结果价值

与矩阵行 5 HBM-only 复制被证伪同构的教训已经在手：**凡是往
稀缺 HBM 里塞常驻东西，先问驱逐外部性**。如果实验判否，这是
一个干净的负结果："LUT 的收益受 tier 容量 regime 限制"——
正好是矩阵喜欢的"否在哪个环节、边界在哪"格式。

注：v8 并发实测里 LUT 与 0.70 mem-util 的 KV 共存没出事
（fact_acc 0.9551、吞吐 99.9 sess/h），说明 1 GB 在**当前**
serve 配置下不是瓶颈；testbed 的 sp96 是人为收紧的容量 regime，
专门用来量边界。

## 4. 交点 B：LUT = 训练时预聚合的 Content Store（叙事，不用实验）

矩阵行 7（PIT）消的是**请求时**并发同需求的重复计算，收益 ∝
时间重叠度（闭链风暴成立，open-loop 错峰判否，15 号 §8）。

LUT 消的是**所有未来 token** 对同一 shared_expert FFN 的重复
计算：表在训练时把"同一函数反复求值"聚合成了"一次训练 + O(1)
查表"。两者是同一个思想——**把重复劳动合并成一次**——在时间轴
两端的实例：

| | PIT（行 7） | LUT（v6） |
|---|---|---|
| 聚合时点 | 请求时（in-flight） | 训练时（offline） |
| 消的重复 | 并发同前缀的重复 prefill | 所有 token 的重复 FFN 计算 |
| regime 变量 | 时间重叠度 | 替换覆盖率 × 调用次数 vs 表存储+查表开销 |
| 代价 | waiter 挂起、backstop | ~1 GB HBM + 查表 kernel |

这给 16 号 §6"消三类重复"提供了一个叙事上的第四类：
named state 消 after-production reuse / across-tier preservation /
in-flight aggregation；LUT 消 **pre-materialized computation**——
把计算本身变成按内容命名的预聚合答案。这是定位陈述，不是实验
结论。

## 5. 交点 C：LUT 改变矩阵各行的相对经济学（候选方向，需证据）

LUT 替掉 FFN 计算后，prefill/decode 的单位成本从 compute 偏向
memory/attention。这会**翻转矩阵两类机制的相对价值**：

- **计算去重类（行 7 PIT）的边际价值下降**：省的本就是计算，
  计算变便宜后省的也变少。
- **存储管理类（行 4 分层驻留、行 5 放置）的相对价值上升**：
  内存成为更紧的瓶颈后，KV 的召回/放置更值得优化——而 LUT
  自己也在吃这份内存（回到交点 A）。

**注意纪律**：这是假设不是结论。按矩阵政策，"LUT on/off 对
行 7  saved_tok 的弹性"是可测的（风暴 regime 下同一 bench 开
关 LUT 比 saved_tok），但目前**没有数据**，本文不写成立。

与 42-reflection 否掉的吞吐扫描的区别：吞吐扫描回答"LUT 本身
快不快"（结构已知，无需实验）；交点 C 回答"LUT 和 ICN 是互补
还是互抢"——两条工作线的战略关系问题。

## 6. 与 v9 扩线的关系

交点 A 的实验不依赖扩层：L37-39 bundle 现成。但**优先级低于
v9 等价性验证**——v9 决定"便宜采样路径能不能产出质量合格的
表"（扩层的前置），交点 A 决定"表在容量紧 regime 下是否净赚"
（部署边界）。两者独立，可并行设计、顺序执行。

3. 不在本文承诺交点 C 的任何数字（§5）。
